## 二、已实施：导入性能 19.7s → 2.5s

### 改了什么（`backend/etl/import_excel.py`）

**问题**：原实现每行 `session.add(doc); session.flush()`，为拿 `doc.id` 而**每行一次 INSERT 往返**。
实测手机膜批次共 **9315 条 SQL 语句**。

**为什么不能简单「加个 add_all 再 flush 一次」**：
MySQL **不支持 `INSERT ... RETURNING`**，ORM 无法在一次 flush 里既批量插入又拿到主键，
SQLAlchemy 会退回逐行插入。因此改成**显式三段式**：

1. `insert(PartDoc)` 多值批量插入（每 500 行一条语句，不带主键）
2. 一次 `SELECT id, row_idx WHERE batch_id, part` **回捞主键映射**
3. `insert(ApprovalNode)` 多值批量插入

失败保护：回捞主键数与被插入行数不一致时**直接抛错中止**（事务回滚，不会留下半份数据）。

顺带把清旧数据从「先查 id、再按 1000 个 id 分批 IN 删子表」改为**一条 JOIN DELETE**。

### 实测结果（同一把尺子）

| 指标 | 改前 | 改后 |
|---|---|---|
| 导入耗时（无 profiler） | **19.7s** | **2.45 ~ 2.77s** |
| SQL 语句数 | 9315 | **271** |
| Python 函数调用数 | 11.59M | 6.93M |
| 数据一致性 | — | 见下方三重验证，**全部通过** |

### 正确性验证（三重，全部通过）

重构涉及「插入顺序」与「主键获取方式」的改变，因此做了三层验证：

1. **行数**：全库 `part_doc` `10027 → 10027`、`approval_node` `34929 → 34929`；
   该批次 2135 单据 / 7173 节点不变。
2. **新旧实现逐行比对**：把 `git HEAD` 的旧模块导出，对同一批 Excel 逐行构造记录并比对
   → **2135 行逐字段完全一致，0 差异，键顺序也一致**（脚本 `verify_equiv.py`）。
3. **库内落盘内容 vs Excel**：对 Part1/3/5/8 共 **1780 行**，比对 `sku / model /
   approval_no / status / raw` 与 Excel 推导值 → **0 条不一致**（脚本 `verify_db2.py`）。

`pytest tests/ -q` → **110 passed**（重构前后一致）。

### 为什么 `raw` 瘦身被否决（推翻第一版结论）

第一版基于「载荷体积主导」的假设，声称把 `raw` 从 83 列瘦身到被读的少数键
可让写入量降到 5.8%。**实测不支持这个假设**：

| 方案 | 导入耗时 |
|---|---|
| 全量 raw（当前实现） | 2.45s |
| 只留 19 个被读的键 | 1.79s |
| **完全不要 raw（理论下限）** | **1.98s** ← 反而比瘦身更慢 |

即使把 `raw` **整个删掉**，也只省不到 1 秒 —— 且不同模式之间差异已在噪声范围内
（同配置两次测量可差 40%）。

**风险面还很大**（这是决定不做的主因）：
- `raw` 会被**原样透传进接口响应**（`review.py:146`、`alerts.py:140` `"raw": raw or {}`）；
- 键名有一部分**来自配置表而非字面量**：`review.NODES` 的 `sys_field` 10 个、
  `alerts._SYS_COLS` 4 个，靠 grep 字面量**必然漏**；
- 读代码才发现的额外键：`到货渠道仓`、`官方发布时间`。

→ **收益 <1 秒，风险是「静默丢掉下游要用的字段」，不做。**

### 一个重要的测量陷阱

1. **cProfile 会严重放大 CPU 段、对 I/O 等待几乎无影响。** 改后 cProfile 报 6.68s，
   而真实墙钟只有 2.45~2.77s —— 差在 openpyxl 那堆百万级小函数调用上。
   **对比优化前后必须用同一工具**，但**对外报数要用无 profiler 的墙钟**。
2. **微基准绝不能在循环里 `commit()`** —— 那是 fsync 路径，会得到比真实情况高 **300 倍**的假数字。
   真实 ETL 是**单事务 + 每行 flush**，基准必须复刻这个模式才对得上账。
3. **批量化在小样本上收益不明显**（1.2–1.4×），但在真实工作负载上是 **7×**。
   小样本微基准**不能替代**端到端实测。

## 三、`/api/overview` 与 `/api/alerts` 的冷启动

### `/api/overview/{batch}`

实测同一个接口连续 5 次：

```
第1次 2.908s   ← 冷
第2次 0.042s
第3次 0.036s
第4次 0.048s
第5次 0.031s   ← 热
```

**按目录指纹的缓存已经在工作**，「3.5s」是**后端重启或 Excel 更新后第一个访问者的一次性代价**。

### ✅ 已实施：空闲预热（`backend/app/prewarm.py`）

覆盖全部三处进程内缓存（全后端只有这三处）：

| 缓存 | 键 | 惠及 |
|---|---|---|
| `analysis._cache` | 批次目录指纹 | overview / timeliness / anomalies / records / compare |
| `review._cache` | DB 指纹 + 规则版本 | review / transport / routes / watch / scenarios |
| `alerts._cache` | 同上 | /api/alerts |

**实施过程中被实测否掉的第一版**（记录在此以免重走）：
第一版是「启动后立刻在后台线程全量预热」。A/B 实测**反而更慢**：

| 首个访问耗时 | 关闭预热 | 立即预热 |
|---|---|---|
| `/api/overview/手机膜9.7` | 2.39s | **5.45s** |
| `/api/alerts` | 2.55s | **5.18s** |

原因是单进程 pandas 预热与用户首次请求**抢 CPU**（GIL），且 `get_batch_data` 的按批次锁
让用户请求只能排队等预热算完同一批次 —— 12.77s 的预热窗口正好盖在用户打开页面的那几秒上。

**改成礼让式**：启动后先等 `PREWARM_DELAY`（默认 10s，覆盖「浏览器已开、前端仍在加载模块」
这段后端看不到请求的空窗），之后**每个预热项之前都检查空闲**，连续 5s 无访问才动手；
持续有访问超过 300s 则放弃本轮。**它绝不与真实使用并行，因此不可能比不做更差。**

改后 A/B（每组都是全新进程）：

| 指标 | A · `PREWARM=0` | B · 默认（空闲预热） |
|---|---|---|
| 首访 `overview/手机膜9.7` | 1.12s | 1.57s |
| 首访 `alerts` | 2.51s | 1.29s |
| **切换批次合计**（另 3 个批次） | **3.43s** | **0.11s** |
| 预热自身开销 | — | 3.25s（全在空闲期，用户无感） |

→ **首访无回归**（两次独立 A/B 都是噪声级差异），收益落在**用户没打开过的批次**上：**31×**。
另一次独立 A/B 的对应数字：首访 `2.15s → 2.17s`，同样无回归。

另加两处接线（否则「导入 / 改规则后缓存刚失效、下一个访问者又得等」）：
- `POST /api/etl/import`：有批次真正入库时，后台登记一次预热补跑；
- `PUT /api/rules` 与 `/api/rules/reset`：规则版本变化会同时让 review / alerts 失效，同样补跑。
接线已用 TestClient 走真实端点验证（导入 HTTP 200、两条补跑日志都如期出现）。

开关：`PREWARM=0` 关闭，`PREWARM_DELAY` 调启动等待秒数。**测试环境自动跳过**
（`with TestClient(app)` 也会走 lifespan，不跳过会拖慢测试并可能造成偶发失败）。

### 已排除 / 其余备选

| 方案 | 做法 | 冷启动 | 结论 |
|---|---|---|---|
| ~~立即预热~~ | 启动后在后台线程全量预热 | — | ❌ **实测让首访慢一倍**（见上） |
| P1-2 落盘缓存 | 按指纹存 `backend/state/cache/<batch>-<fp>.pkl` | ~0.2s | 未做。pickle 与 pandas 版本耦合，需版本戳 + 回退 |
| P2 架构级 | `analysis.py` 改从 MySQL 读（ETL 已入库） | — | 未做。可消除「Excel/DB 两份真相」，但需重写数据访问层 |

### `/api/alerts`

干净进程下实测：

```
第1次 2.740s   ← 冷（首次计算）
第2次 0.0145s  ← 热
第3次 0.0121s
```

分段计时（独立进程）：`_load_all_docs()` 0.58s + `get_review_data()` 1.25s +
`compute_alerts()` 0.60s ≈ 2.4s —— **计算本身并不慢**，问题同样是「冷启动一次性代价」。

> ⚠️ **一次未复现的挂起**：在**旧后端进程**上，`/api/alerts` 曾有一次超过 6 分钟不返回
> （客户端 90s 超时后重试仍挂），杀掉进程重启后一切正常、且冷启动仅 2.74s。
> 已排查并**排除** ABBA 死锁：`alerts` 与 `review` 的锁获取方向虽交叉
> （alerts 持锁后调 `review.get_review_data()`），但 `review.get_review_data()` **从不持锁**
> 去获取 alerts 锁（`record_snapshot` 被刻意放在锁外，见 `review.py:728` 注释）。
> **无法复现，故不下结论。** 若再次出现，优先看：请求是否排在一个被客户端中断的旧请求后面、
> 以及是否有并发的长事务（批量导入）持有行锁。
> **空闲预热（P1-1）同样覆盖这里**：`alerts._cache` 与 `review._cache` 都在预热清单中，
> 且 review 先算、alerts 复用它，不会重复计算。

> 现有 `_cache` 是**进程内无上限**字典（review / alerts 各一份）。当前 4 个批次可接受；
> 批次数量增长需加 LRU。缓存键为 `批次的 imported_at 最大值 + 规则版本`，
> **每次导入都会让两份缓存同时失效**。

## 四、前端

### 深色模式

**有利条件**：硬编码色值已 **0 处**（全走 `SEMANTIC`）；`components/EChart.jsx` 是唯一图表出口，6 个页面共用 → **单一改造点**。

**真正的难点**：17 个页面在**模块作用域**直接 `import { SEMANTIC }`，颜色是**编译期常量**，
运行时切模式不会变色。这是深色模式的主要成本，不是配色本身。

- **方案 A（推荐，~3 个文件）**：把 `SEMANTIC` 的值改成 **CSS 变量**（`var(--sem-danger)`）。
  MUI 的 `sx` 原生支持 CSS 变量 → DOM 侧**所有页面零改动**自动跟随。
  图表侧在 `EChart.jsx` 用 `getComputedStyle` 解析变量值，并监听模式切换重绘。
- **方案 B（干净但贵）**：`SEMANTIC` 改成 hook（`useSemantic()`）→ 17 个页面全部改。不建议先做。

配套：`theme.js` 出 `makeTheme(mode)`；ECharts `init(el, 'dark')`；AppBar 加切换按钮 +
`localStorage` + `prefers-color-scheme` 跟随。

### 响应式

实测改造面：

| 项 | 现状 |
|---|---|
| App 布局 | 固定 `Drawer`，**无 `useMediaQuery`** |
| Grid 使用 | 79 处，仅 **11 个页面**写了断点 |
| `TableContainer` | **14 个页面已用** → 表格横向滚动基本白送 |
| 硬编码宽度 | 29 处待复核 |

建议顺序：
1. App 的 `Drawer` 在 `< md` 切 `temporary` + AppBar 加汉堡按钮（**先做这个，其余才有意义**）
2. KPI 卡网格补 `xs={12} sm={6} md={3}`
3. `PageHeader` 在 `< sm` 纵向堆叠
4. Gantt 时间轴横向滚动
5. 复核 29 处固定宽度

## 五、大文件拆解

`review.py` 956 行、`alerts.py` 542 行的**真实危害**不是行数，而是**计算逻辑混在路由里 →
无法单测**（9-14 新增的 6 个模块至今零测试覆盖）。

做法：抽 `app/services/`，路由只做「解析参数 → 调 service → 序列化」。
- 拆分原则：**纯函数先搬**（搬完立刻能补测试），副作用留在路由层。
- 时机原则：**在你下次真要改它的那一刻拆**，不要为拆而拆。
- 参考切法：`review.py` → `review_docs` / `review_export` / `review_kpi`；
  `alerts.py` → `alerts_rules`（纯计算）+ `alerts_api`。
