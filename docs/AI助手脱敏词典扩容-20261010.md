## 1. 为什么要扩（一句话）

「数据不出外网」承诺的**技术兜底只剩脱敏这一道**（分级授权/告知是人看的）。脱敏判据 = 一本**键名子串**词典，**词典里没有的词，引擎就认为不敏感、直接出网**。实测词典不足以覆盖业务里真实出现的字段名。

## 2. 取证方法（不是拍脑袋，是打了真数据）

起平台后端 `:8000`，**逐个 `platform_*` 工具对应的端点**（两品类）取真实响应，递归收集**所有 dict 键名**：

```
GET /api/batches?category=…            GET /api/overview/{batch}?category=…
GET /api/records/{batch}/{part}?…      GET /api/alerts?category=…
GET /api/transport?category=…          GET /api/inflight?category=…
GET /api/inflight/alerts?category=…    GET /api/inflight/daily-report?category=…
GET /api/deltas?days=30&category=…     GET /api/review/sku/{sku}?category=…
GET /api/routes?category=…
```

> 为什么打这些端点就够：Agent 侧 `plugins/workmain.py::_out()` 是把**平台 API 的原始 JSON** 交给 `_plat_sanitize(obj)` 逐键过滤后再渲染的 ⇒ **真正会被词典判定的键集合 = 平台 API 响应里的键**。
> 探针脚本：`_probe_sens_keys.py`（临时件，`_*` 已 gitignore，可复跑）。

**结果：499 个唯一键**。

| 真实键 | 出现端点 | 旧词典(23) | 结论 |
|---|---|---|---|
| `owner` | inflight / inflight_alerts / review_sku | ✅ 已挡 | — |
| `operator` | records / deltas | ✅ 已挡 | — |
| `当前负责人` | records | ✅ 已挡（含「负责人」） | — |
| `创建人` / `创建人部门` | records | ✅ 已挡（含「创建人」） | — |

在这些端点里**并未作为键出现**（0 命中）——但它们是**同类衍生风险**（本系统数据源就是钉钉审批导出，
`records` 里已经出现 `历史审批人` 说明表单字段会以键形式透出）。⇒ 按下节一并补为**加固**。

## 4. 取证结果二：**禁止加裸 `name`**（这条最值钱）

候选词 `name` 在真实键集上命中 **5 个键**，而它们**全是合法业务键**：

```
name          ← /api/batches 的批次名（"手机膜"）
l4Name        ← 复盘段级名
partName      ← Part 名
pendingPartName ← 加急页的待处理 Part 名
_partName     ← records 内部字段
```

⇒ **把裸 `name` 加进词典会一次把批次名 / Part 名 / 段名全部剔除**，助手立刻「问瞎」。
**结论：name 族只收具体复合词**（`username` / `customername` / `realname` / `fullname`），
**永久禁止加入裸 `name`**（已写成单测 `test_expansion_forbids_bare_name_token` 守住）。

## 5. 取证结果三：发现 **2 个既有缺陷**（本轮**不修**，需显式同意）

### 5.1 裸 `手机` 误伤业务字段（既有行为，非本轮引入）
旧词典含裸 `手机`（本意是挡「手机号」），但真实数据里它把 **4 个业务字段**一并剔除了：

| 被误剔的键 | 它是什么 |
|---|---|
| `手机膜类型` | 膜品类字段 |
| `手机数据取得日期` | 关键时间指标 |
| `手机数据取得时间` | 关键时间指标 |
| `手机壳确样日期` | 壳确样时间 |

**证据**：真实数据里**没有任何**「手机」开头的敏感键（人员键是 owner/operator/executor/…，与「手机」无关）；
而 11 位手机号**另有值级正则 `(?<!\d)1[3-9]\d{9}(?!\d)` 兜底**（与键名无关）。
⇒ 裸 `手机` 的键级剔除**对它的原本目的几乎没有贡献，却在丢业务数据**。

**建议改法**：`手机` → `手机号`。
**为什么本轮不做**：这是**放宽**安全过滤器，属「需要显式同意」的变更；且与「只增不减」纪律冲突。
（若同意，两侧同步改，并把单测 `test_known_overblock_by_bare_mobile_substring_documented` 翻转为「保留」。）

### 5.2 `phone` 误伤型号名
`Nothing Phone 3a 5G` 在 `inflight` 里**作为键**出现（型号名当 key），被 `phone` 剔除。
属同类误伤，影响面小（同一型号另有 `model` 字段可取）。**建议保持现状**（英文 `phone` 是真敏感词干）。

## 6. 本轮扩容清单（平台侧已实装：23 → **57** 条）

机制**不变**：`str(k).lower()` 后**子串**匹配，命中即**整键剔除**；大小写不敏感。

| 分组 | 条目 |
|---|---|
| 对齐 Agent 侧（不得删） | `负责人 操作人 创建人 姓名 手机 电话 联系方式 备注 owner creator operator phone mobile remark` |
| T10 上轮 | `联系 邮箱 email mail 微信 wechat 身份证 idcard contact` |
| **真实命中·必加** | `executor`、`审批人`（覆盖 `历史审批人`） |
| **中文职务/身份** | `申请人 审核人 经办人 对接人 主管 收货人 收件人 寄件人 处理人 提交人 跟进人 执行人` |
| **主体标识** | `用户 客户` |
| **联系方式** | `地址 座机 固话 传真` |
| **英文对应** | `handler approver applicant receiver consignee shipper addr tel fax qq` |
| **name 族（禁裸 name）** | `username customername realname fullname` |

> 冗余项（如 `telephone`、`address`、`ownername`、`手机号`、`联系电话`）已剔除 —— 被 `tel`/`addr`/`owner`/`手机`/`联系`/`电话` 覆盖，不必重复。
