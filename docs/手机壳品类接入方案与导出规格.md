# 手机壳品类接入方案 与 导出规格差异清单

> 日期：2026-09-21
> 背景：数据后台系统原本只接入手机膜（4 个批次）。现需接入手机壳（1 个批次）。
> 排查结论：**代码侧是小改动；真正的阻塞在"自动同步导出的 `审批记录` 缺业务节点名"。**

---

| 事项 | 结论 |
|---|---|
| 数据目录 | `data/<品类>/<批次>/Part1~9.xlsx`，手机壳结构与手机膜**同源** |
| 数据后台系统代码 | **几乎与品类无关** —— 全仓仅 6 个文件提到"手机膜"，只有 `config.py` 的 `DATA_ROOT` 是功能性的 |
| 同步工具 | `dingtalk/approval_sync.py` —— 已支持手机壳（`config.json` 里 9 个 `PROC-` 编码齐全） |
| ~~唯一阻塞~~ | ~~自动同步产出的 `审批记录` 里没有业务节点名，30 个关键动作只命中 9 个~~ |
| **现状（2026-09-21）** | ✅ **已修复并验收**：手机膜关键动作 **30/30 = 100%**，与手工导出逐行一致率 90%+ |
| 列结构 | 同品类下 6/9 个 Part 完全相同，另 3 个各多 1 列（表单改版新增字段，**必须保留**）→ 不是问题 |

**修复要点**（详见第二、三节）：调 `workflow/processes/forecast` 把
`activityId` 还原成节点名（零人工、无需手工导出校准）；用 `activityActioners`
的 `{userId, name}` 反查姓名（绕开未开通的通讯录权限）；离职人员用手工导出
一次性补种；抄送节点按「前序审批节点完成」的链序归属；**列只增不减**。

## 一、事实与证据

### 1.1 同样一份"手机膜"，两种导出的差别

| 来源 | 路径 | 动作名种类 | 操作人 | 30 个关键动作命中 |
|---|---|---|---|---|
| **手工导出** | `data\手机膜\手机膜9.7\` | **45 种** | 姓名（如 `巨川电子`） | **30 / 30** |
| 手工快照 | `dingtalk\_backup\manual_snapshot_20260918\` | 53 种 | 姓名 | — |
| **自动同步** | `data\手机膜\手机膜\` | **7 种** | 数字 ID | **9 / 30** |
| **自动同步** | `data\手机壳\手机壳\` | **4 种** | 数字 ID | 预计 **9 / 30** |

### 1.2 用户可见后果（当前线上就有）

`GET /api/timeliness/手机膜`（读的就是自动同步那份）——**9 个 Part 全部为 null**：

| Part | 手机膜（自动同步） | 手机膜9.7（手工导出） |
|---|---|---|
| 产品开发 | **null** | 26.42 |
| 新品首单下单 | **null** | 287.02 |
| 新品本地仓到货 | **null** | 250.99 |
| 新品渠道仓发货 | **null** | 546.88 |
| 新品渠道仓到货 | **null** | 927.74 |

预热日志同样印证：`手机膜` **4353 条异常** vs `手机膜9.7` **866 条**（假异常暴增）。

### 1.3 根因

`dingtalk/approval_sync.py` 的 `action_text()`（约 325 行）只把
`operation_records[].operation_type` 映射成动作名：

```python
'START_PROCESS_INSTANCE'    -> '提交申请'
'EXECUTE_TASK_NORMAL' + AGREE  -> '同意'      # ← 业务节点名在这一步丢失
'EXECUTE_TASK_NORMAL' + REFUSE -> '拒绝'
'PROCESS_CC'                -> None           # ← 抄送节点被整条丢弃
```

例：某张 Part1 单据在手工导出里是

```
张智博|提案确认|2026-08-26 10:10:40|;
```

自动同步产出的却是

```
575626634026256812|同意|2026-08-26 10:10:40|;
```

两侧**时间完全一致**，只是"提案确认"被写成了"同意"。下游 `parser.get_key_action_time()`
用**精确相等**匹配动作名，于是永远取不到时间 → 分段耗时为 0/空 → 时效看板全空。

`operation_records` 里**也没有 `activity_id`**，所以事后无法自愈；
但实例详情的 **`tasks[]` 带 `activity_id` + `finish_time`**（如 `ab6e_7e5d`），这是可用的抓手。

## 二、【交给同事】导出侧必须补齐的字段

### 2.1 核心：`审批记录` 的动作名必须是**流程节点名**，不能是"同意/同意/同意"

- 输出格式保持现状即可：`操作人|动作|时间|备注;` 多条用 `;` 分隔。
- **动作名 = 该审批节点在流程模板里的名称**（即 `activityName`），例如
  `提案确认`、`取得手机数据`、`产品信息补充`、`发货`、`到货通知`、`采购下单`…
- 一般审批节点的 `operation_result` 仍用于区分**同一节点**的同意/拒绝语义，
  但**动作名必须是节点名**。参考手工导出的写法：节点名进"动作"位，同意/拒绝体现在"备注"或省略。

### 2.2 逐 Part 必须出现的动作清单（合计 30 个，这是验收基线）

括号内为该动作在手工导出 `手机膜9.7` 中的出现次数，可用于核对量级。

| **Part2 新品首单下单** | 提交申请(76)、**站点需求收集(79)**、**特殊需求数量收集(78)**、**全套样品测试完成(67)**、**采购下单(62)** |

**当前自动同步的产出**：除"提交申请"外，**上表加粗的 21 个动作全部为 0**。

### 2.3 抄送（CC）节点不能被丢弃 ✅ 已在导出侧解决

`PROCESS_CC` 原来直接返回 `None`（整条不写）。但 `通知_手机数据已取得` 是
**Part1 关键动作链的一环**，手工导出里它出现 154 次。

**已实现**：抄送节点按「它的前序审批节点完成」这一触发关系（`activity_nodes.prev_id`
链序 + 同秒判定）归属到具体节点，动作名用该 CC 节点的名称，格式对齐手工导出：
`收件人|通知_产品立项|2026-08-10 17:52:41|抄送`。

两种特殊情形一并处理：

- **或签被取消的人** —— 手工写成 `某人|节点名（抄送或签审批人）|时间|抄送`，
  按「该时刻刚通过的审批节点存在被取消的或签成员」识别。
- 同一个抄送节点**只允许被认领一次**（早期版本漏了标记，会把 3 条抄送记录
  全写成同一个节点，已修）。

### 2.4 操作人必须是**姓名**，不是 userid ✅ 已解决（无需通讯录权限）

- 原来：`575626634026256812` 这类数字 ID。原因：通讯录读权限
  `qyapi_get_member` 未开通，`users` 表只有 5 条。
- **零权限解法**：`forecast` 返回的 `activityActioners[]` 每项同时带
  **`userId` + `name`** → 顺手反查就能建出 userid→姓名表（现已 19 人）。
- **离职人员**（`杨晓莹(已离职)`、`谢雪娜(已离职)`、`王琴` 这类）已经不在任何
  节点的当前处理人名单里，forecast 拿不到 → 用一份**手工导出做一次性补种**：

  ```
  python approval_sync.py --seed-names "C:\...\dingtalk\_backup\manual_snapshot_20260918"
  ```

  把两侧「审批记录」按 **(动作名, 时间)** 对齐（实测对齐样本 9112 组），
  对 `userid → 姓名` 投票，绝对多数才写入，且**只补不覆盖**。已补进 25 个姓名。

> 通讯录权限仍建议开通（能自动覆盖以后新出现的离职人员），但**已不再是前置条件**。

### 2.5 列结构：新增列**必须保留**，不能为了「跟手工对齐」删掉 ✅

同品类（手机膜）手工导出 vs 自动同步，逐 Part 比对
（`python scripts/check_column_parity.py`，退出码 0）：

| Part | 结果 |
|---|---|
| Part3 / Part5 / Part6 / Part7 / Part8 / Part9 | **列完全相同** |
| Part1 | 同步多一列 `官方发布信息渠道` |
| Part2 | 同步多一列 `站点需求收集` |
| Part4 | 同步多一列 `印度` |

⚠️ **这三列是表单后来新增的字段，必须保留**，不是缺陷。

手工导出是**旧时间点的快照**（9.18），表单之后加了字段，所以两边列不完全一致
是正常的。判定口径要按**文件名的快照时间戳**（不是 mtime —— 快照被复制备份过，
mtime 会变成复制时刻）：

- ★ **新增列**（较新一方有、较旧一方没有）= 表单改版新增字段 → **保留**
- ⚠ **缺失列**（较旧一方有、较新一方没有）= 真正的回归 → 必须查因

导出侧已实现「只增不减」：列基线按时间戳取、多份快照做并集、DB 里固化过的列兜底，
新字段按出现顺序追加，并在日志留痕 `新增列 N 个（表单新字段，保留）`。

**手机壳目前没有手工快照**，对它跑列对照会拿错同名基线（会误报 12 个"缺失列"）
→ 检查脚本默认只查手机膜（`--products 手机膜`），手机壳需要它自己的一份手工导出。

### 2.6 其他需要保持一致的点 ✅ 已核对一致

| 项 | 手工导出 | 自动同步 |
|---|---|---|
| **审批单标题** | `巨川电子提交的Part2_新品首单下单` | 同左（**已一致**） |
| 明细表（TableField） | 不含 | 不含（一致，README §6.4 已说明） |

> 早期版本的自动同步会把标题里的下划线写成连字符（`Part2-新品首单下单`），
> 2026-09-21 复核已一致，此条关闭。

## 三、【技术路线】怎么拿到"节点名"

### 3.1 首选：调官方接口取节点名 ✅ 已实测跑通，已落地

**`POST https://api.dingtalk.com/v1.0/workflow/processes/forecast`**（获取审批单流程中的节点信息）

- 请求体需 `processCode` + `deptId` + `userId` + `formComponentValues`
- 返回 `result.workflowActivityRules[]`，每项含：
  - **`activityId`** —— 节点 ID
  - **`activityName`** —— **节点名称**（就是要的东西）
  - **`prevActivityId`** —— 前一节点（用来还原链序与抄送触发关系）
  - `workflowActor.actorType` —— `approver` / `audit` / **`notifier`**（抄送/通知节点）
  - `activityActioners[]` —— **`{userId, name}` 成对**（顺带解决姓名问题）
- 另有 `result.workflowForecastNodes[]`（`activityId` + `outId`）描述节点流。

**结论：`activityId` 与实例详情 `tasks[].activity_id` 是同一套编码**（`ab6e_7e5d` 这种），
直接建 `activityId → activityName` 映射表即可，**零人工、无需任何手工导出做校准**。
18 个模板（手机膜/手机壳 各 9 个）全部学习成功，已落库 `sync_cache.db.activity_nodes`。

两个实测坑：

1. **`userId` 必须是还在职的人** —— 传离职账号会返回 `userNotExist`。实现里会从
   本单出现过的人里挑一个在职账号重试。
2. 旧接口 `/topapi/process/template/get`、`/topapi/process/get` **已下线**
   （返回"不合法ApiName"），不要再用。

### 3.2 备选（已备而不用）：用手工导出做一次性校准

`activityId` 与 `tasks[].activity_id` 已确认同一套编码（见 3.1），**这条备选路线不再需要**。

不过「手工导出当真值」这个思路仍有一处**在用**：给**离职人员补姓名**——
`python approval_sync.py --seed-names <手工快照目录>`（见 2.4）。
离职人员不在任何节点的当前处理人名单里，API 拿不到，只能拿历史真值反查。

## 五、【需要业务确认】手机壳与手机膜的流程差异

用户印象是"流程几乎一模一样"，但**数据不支持**：Part1/2/3/6/7/8 的列与关键步骤都不同。

### 5.1 列差异（手机壳 Part1~9 vs 手机膜）

| Part | 手机膜独有 | 手机壳独有 |
|---|---|---|
| Part1 | `手机数据取得日期`、`产品SKU`、`产品图片`、`手机膜类型`、`目标区域`、`官方发布信息渠道（市场/非市场）`、`官方发布时间`、`亚马逊上架或预计上架时间` | `三方确样时间`、`全部设计确认时间`、`打样完成时间`、`新品SKU`、`设计稿图片` |
| Part2 | `全套样品测试完成时间`、`手机数据取得日期`、`是否真机测试`、`供应商售后承诺书（非真机必填）`、`目标区域` | `三方确样时间` |
| Part3 | `手机数据取得时间` | `手机壳确样日期` |
| Part4 | — | — （完全一致） |
| Part5 | — | — （完全一致） |
| Part6 | `是否决定拍摄`、`素材参考SKU`、`素材参考型号` | — |
| Part7 | `手机数据取得时间` | `手机壳确样时间` |
| Part8 | `到货数量`、`手机上架日期` | — |
| Part9 | — | — （完全一致） |

⚠️ **其中 3 个是当前配置登记的"业务时间列"**：手机膜的 `手机数据取得日期`(Part1)、
`全套样品测试完成时间`(Part2)、`手机上架日期`(Part8) —— 手机壳**都没有**。
→ 手机壳的对应口径需要业务确认（是否用 `三方确样时间` / `打样完成时间` / `手机壳确样日期` 替代？）。

### 5.2 结构差异：手机壳也有"设计→打样→确样"环节

从列名可推断手机壳流程含**设计/打样/确样**（`设计稿图片`、`打样完成时间`、
`全部设计确认时间`、`三方确样时间`、`手机壳确样日期`），而手机膜是
**取得手机数据 → 产品信息补充 → 全套样品测试**。这两条链不对应。

→ 需要业务给出**手机壳的 9 个 Part 关键动作链**（哪个环节算哪个步骤的起止）。

### 5.3 手机壳的业务时间其实在"表单列"里

实测手机壳表单含完整业务时间列：`发货日期`(67)、`渠道仓到货时间`(58)、`三方确样时间`(46)、
`全部设计确认时间`(34)、`打样完成时间`(34)、`首单下单时间`(17)、`全站点首次上架完成日期`(17)、
`本地仓到货时间`(7)、`最终上架完成时间`(7)、`广告上架完成时间`(7)…

⚠️ 但这些列的时间与审批节点 `finish_time` **零对齐**，所以**不能用它们反推节点名**。
它们是**备选取数口径**（直接按列取时间，不依赖审批记录）—— 代价是手机壳与手机膜口径不一致
（没有 Part 内分段时效），**不推荐**，除非导出侧实在修不动。

导出侧修完后，用这三条验收，全过才算"达到手工导出的效果"。

3. **列结构无回归**（`scripts/check_column_parity.py`，退出码 0）

   ```
   python scripts/check_column_parity.py            # 默认只查手机膜
   ```
   手机膜：**0 个缺失列**，3 个新增列（表单改版新增）全部保留。

4. **时效非空**

   ```
   curl --noproxy "*" "http://127.0.0.1:8000/api/timeliness/<批次>"
   ```
   `partBar` 的 `avg/median/p90/count` 不能全为 null。

5. **异常数合理**

   预热日志里该批次的异常条数应与手工导出同量级（例如手机膜 866 左右，
   而不是几千条）。

### 6.1 已知残余差异（不阻塞，均已定位）

| 项 | 现状 | 说明 |
|---|---|---|
| 抄送行的**收件人** | 用节点当前处理人，逐单真值拿不到 | forecast 的 `activityActioners` 是**模板级**静态名单，按单传表单值也返回同一套；实例上的 `cc_userids` 是**全单并集**，拆不到具体节点。`operation_records.userid` 恒为触发人，不是收件人。→ 只能保证节点名与时间正确，收件人在个别模板上会与手工略有出入 |
| 老单据的**节点名** | 用**当前**模板名 | 模板改版后节点被改名（如 `产品主管` → `取得手机数据`）。下游按当前名匹配，用当前名反而是对的 |
| **手机壳**关键动作 | 22/30 | 手机壳流程本身不同，需业务给关键动作链（见第五节） |
| 手机壳**列对照** | 无法做 | 缺手机壳自己的手工快照 |

## 七、附：为什么不能"先把手机壳接进去再说"

接进去不会报错，页面也打得开——**但所有时效指标都是空的**，
而且异常列表会因为"关键动作取不到时间"而**暴增几千条假异常**。
这种"看起来正常、数据全错"的状态比直接打不开更危险：同事会照着空看板做判断。
所以必须**先修导出、再接品类**。
