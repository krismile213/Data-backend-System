## 一、现有复盘体系总结（平台要承接的东西）

### 1. 三套分析口径（已是成熟 Python 程序，已移植进平台）

| 程序 | 口径 | 核心输出 | 平台落点 |
|---|---|---|---|
| `review.py` | 大流程复盘 | 复盘对象筛选（三部门终节点 + 3~8月窗口）、7 个 sheet | ✅ `backend/app/routers/review.py`（已取消时间窗口，走全量） |
| `route_check.py` | 路线复盘·动作口径 | 运营/后勤路线评级、逐货件运输核对、发货批次明细 | ⚠️ 部分落在 `seg_rules.py` 段级目标 + 复盘货件表 |
| `route_check_sys.py` | 路线复盘·系统口径 | 双轨时间、部门段级判定、SKU 总览、甘特图、异常汇总 | ✅ `seg_rules.py` + `review.py` + `Gantt.jsx` + `alerts.py` |

### 2. 复盘时效规则（已配置化）

- `时效确认规则表.xlsx`：开发类型（常规/提前）× Part1~9 的确认目标天数、是否考核、是否有下游依赖；
- 运输目标：空运 15 / 海运 35 / 卡航 35；发货批次 ≤22 天（L4）。
- ✅ 已落地为 `backend/app/seg_rules.py` 的段级默认目标，并可通过规则配置中心的
  `seg_targets` 在线调整（`GET/PUT /api/rules`），改完复盘与预警立即重算。

### 3. 复盘数据资产（约 90 个型号）

```
复盘文件/
├─ G506~G597/                每 SKU：Part*.xlsx（多版本）+ route_路线复盘.md
└─ 有效复盘_时效报告汇总/      每 SKU 一份动作级时效报告 md（目标/判定/运输核对）
```

### 4. 已实证的业务结论（平台自动诊断的目标）

- **Part5 发货停滞是链条断点**：16 票全停在「提交申请」→ 连锁卡死 Part6 素材 → 页面 coming soon；
- 场景 A（已首上架无素材，最易 coming soon）/ B（差最终上架）/ C（发货未完成）跨 SKU 统计；
- 优化方向：素材启动与 Part5 解耦、跨环节依赖预警、coming soon 去化路径前置。
- ✅ 场景 A/B/C 已于 v2 同日上线为「场景诊断」页（见第二章 #10）。

## 五、实施建议

1. **保持口径单一来源**：所有阈值走 `seg_rules.py`（代码默认）+ `rule_service`（DB 覆盖），
   前端只读不硬编码，避免同一指标多处不一致。
2. **新增能力优先复用复盘引擎**：`review.py` 的 `get_review_data()` 已带缓存与去重，
   新页面（如场景诊断）直接消费其 `skuDetails`，不要另起一套数据装载。
3. **三批划分已过期**：原「第三批需数据库」的前提（MySQL 数据层）已建成，
   实际阻塞项改为**外部条件**（用户体系 / 通知渠道 / 钉钉凭据），后续按第四章排序而非批次数。
