# 流程节点与字段扩展映射指南

> 适用：**新增一个流程节点**、**新增一个数据字段**、**接入一个新品类**时，要改哪里、怎么映射、怎么验证。
> 维护日期：2026-09-22 ｜ 依据：本机真实数据实测（手机膜 4 批次 + 手机壳 1 批次）

---

## 0. 先读这一节：三个同源件的关系与口径

本套复盘逻辑有**三个同源件**，口径必须一致；改一处就要评估另两处。

| 件 | 路径 | 时间口径 | 状态 |
| --- | --- | --- | --- |
| **A** | `流程复盘/route_check.py` | **动作映射口径**：节点 = `Part + 审批动作名`，时间取自 `审批记录` 里的动作时间（不读系统业务时间列） | ⚠️ **保留归档**。不再新增功能，平时不以此为准 |
| **B** | `流程复盘/route_check_sys.py` | **系统口径**：`系统业务时间列` > `audit`（审批记录备注含 audit 的人为上报） > `审批动作时间` | ✅ **主口径，以此为准** |
| **C** | `数据后台系统/backend/app/*` | 移植 B 的段级口径，再叠加在线服务、因果链、损益。**按品类分文件**：`seg_rules.py`（手机膜）/ `seg_rules_shell.py`（手机壳），由 `category_rules.py` 分发 | ✅ 在线服务；逻辑改动需与 B 同步 |

**约定（2026-09-22 确认）**：日常看 B（sys）；A 只作历史对照保留；C 的段级口径以 B 为准。

### 品类分规则代码（2026-09-22 落地）

手机膜与手机壳走**两套钉钉流程模板**（processCode 不同、列不同、节点链不同），
所以**各一份规则代码**，避免后续任一方加节点时互相污染：

| 品类 | 规则文件 | 节点链 | 考核时钟起点 |
| --- | --- | --- | --- |
| 手机膜 | `backend/app/seg_rules.py` | 提案→**取数**→签样→… | **取数** |
| 手机壳 | `backend/app/seg_rules_shell.py` | 提案→**签样**→…（**无取数**） | **提案** |

分发入口 `backend/app/category_rules.py`：`rules_for(品类)` → `RuleSet`
（含 nodes / segs / l4 / route_targets / start_node / part_configs / provisional …）。
引擎（`review.py` / `assessment.py` / `causal.py` / `reporting.py`）新增的
`ruleset=` / `start_node=` 参数**默认取手机膜**，因此手机膜在线行为与改造前逐字节一致。

- 接口可带 `?category=手机壳` 切换（缺省 = 手机膜）。
- `RuleSet.describe()` 会把 `startNode / routeTargets / targetsProvisional / targetsSource`
  一起返回，**避免"静默用了哪套口径"**。
- ⚠️ `seg_rules.py` 仍保持**零改动**（全仓 15 处现存导入全部不受影响）。


### ⚠️ 已知的口径不齐（尚未统一，改动时注意）

| 口径点 | B（`route_check_sys.py`） | C（后台 `review.py`） | A（`route_check.py`） |
| --- | --- | --- | --- |
| **多轮提交配对** | **取「最早一轮」**（2026-09-22 改） | 取「取数日期与该轮创建时间**最接近**」的一轮 | 未处理 |

- G506 上两者结果一致（都归到第 1 轮 → `提案→取数 = 0 天`），所以问题未暴露。
- **分歧场景**：「第 1 轮提案后长期未取数、第 2 轮重新提交并真正取数」——B 会取到第 1 轮（无取数 → 取数节点为空），C 会取第 2 轮（能算出取数）。
- 之所以 C 不用「最新一轮」也不用「最早一轮」：G506 的第 2 轮补报单**把「手机数据取得日期」抄成了第 1 轮的 2025-10-30**，单看日期无法判断归属，必须与「该轮创建时间」比对。

## 1. 全链路映射关系（这就是"映射"的全貌）

```
Excel 列：系统业务时间列（如「本地仓到货时间」）+ 审批记录里的动作名（如「本地仓到货检查」）
   │
   │  ① 节点定义  →  backend/app/seg_rules.py :: NODES
   │     {节点名: (Part, 系统业务时间列, 审批动作, 默认责任人)}
   ▼
节点时间（11 个 + 提案）          取值优先级：系统列 > audit 上报 > 审批动作时间
   │
   │  ② 段定义  →  backend/app/seg_rules.py :: SEGS / L4
   │     段 = (部门, 环节名, 起点节点, 终点节点, 目标天, 责任人, 说明, 是否留空段)
   ▼
段级耗时 / 判定（✗超时、⚠提案超期）      段目标可在配置中心 `rule_config.seg_targets` 热调
   │
   │  ③ 路线评级  →  backend/app/seg_rules.py :: ROUTE_TARGETS
   │     ⚠️ 时钟起点 = 「取数」（不是提案！提案→取数 1 天只挂异常预警，不进考核；
   │        锚点 = Part1「提案日期」，未填回退创建时间，2026-10-19 起）
   ▼
路线总评级（运营/空运/海运 → 优/良/差）
   │
   │  ④ 损益  →  backend/app/assessment.py + product_rules.py
   │     推迟天数 = 空运路线超 60 天底线的天数（空运到货即可开卖）
   │     少卖件数 = 推迟天数 × 评级日均区间（XC = 1.38~5.5）
   │     亏损 = 少卖件数 × 单价（商品资料「参考成本价」）
   ▼
损益区间（件数 / 金额）；提前完成才算**增益**
```

### 各层定义在哪个文件（改哪一层就动哪个文件）

| 层 | 定义位置 | 说明 |
| --- | --- | --- |
| 节点（Part + 系统列 + 动作） | **按品类**：`seg_rules.py::NODES` / `seg_rules_shell.py::NODES` | **单一真源**，探测脚本也读它；系统列支持**候选链**（元组，首个非空生效） |
| 段与目标天 | 同上的 `SEGS`、`L4` | 段目标运行期以 `rule_config.seg_targets` 覆盖；离线件（`流程复盘/route_check_sys.py`）通过 `资产文件\规则快照.json` **跟随规则页值**（T17） |
| 路线评级线 | 同上的 `ROUTE_TARGETS` | 膜：运营 52/60、空运 49/60、海运 69/—；壳：继承（`provisional=True`） |
| 考核时钟起点 | `category_rules.py::RuleSet.start_node` | 膜=取数；壳=提案 |
| 品类分发 | `category_rules.py::rules_for()` | 未知品类回退手机膜，绝不抛异常 |
| 运输目标（按渠道） | 同上的 `transport_mode()` | 空运 15 / 海运·卡航 35 |
| Part 名 / 关键动作 / 业务时间列 | **按品类**：`config.py::PART_CONFIGS`（膜）/ `seg_rules_shell.py::PART_CONFIGS`（壳） | 经 `config.part_configs_for(品类)` 取用；供动作覆盖检查、异常分析用 |

| 部门终节点 / Part 目标时效 | `backend/app/review_rules.py::DEPARTMENTS`、`EFFICIENCY_TARGETS` | 产品部终节点=素材交付（=Part6「产品营销素材加工」；实际以品类规则集 `PRODUCT_END_NODE` 为准） |
| 评级档位 → 日均销量 | `backend/app/product_rules.py` | 从商品资料 A1 **文本解析**并交叉校验 |
| 因果链定位 | `backend/app/causal.py` | 漏报嫌疑 / 搁置 / 运输 三类归因 |
| 损益计算 | `backend/app/assessment.py` | 抽成纯函数便于单测 |
| 报告导出 | `backend/app/reporting.py` | 核查报告 xlsx（含人工核对列）/ 评估三指标 |

## 2. 新增一个「流程节点」的标准步骤

> 例：将来钉钉模板新增「供应商报价确认」节点。

**第 1 步：先探明它在数据里的落点**——是**系统业务时间列**，还是只有**审批动作名**？

```powershell
# 看该品类有哪些列、列名是什么
python scripts/probe_category_columns.py "<批次目录>"
```

- 有系统列 → 走「系统列」路径（推荐，最稳）
- 只有动作名 → 系统列填 `""`，靠审批动作名定位（如现有的「素材加工」）

**第 2 步：改节点定义**（`backend/app/seg_rules.py::NODES`）

```python
NODES = {
    # ... 现有 11 个 ...
    "报价确认": ("Part2", "供应商报价确认时间", "供应商报价确认", "周奕奕"),
    #             ↑Part   ↑系统业务时间列（没有就填 ""）  ↑审批动作名   ↑默认责任人
}
```

**第 3 步：改段定义**（同文件 `SEGS`）——把新节点接进链条

```python
SEGS = [
    # ... 现有段 ...
    ("后勤", "签样→报价确认", "签样", "报价确认", 3, "周奕奕", "新增节点", False),
    #  部门    环节名          起点    终点        目标天  责任人   说明      是否留空段
]
```

> ⚠️ 若新节点插在既有一段中间，要**拆段**（原段改为两段），否则时间轴会出现断点。
> 留空段（`is_gap=True` / 部门 `__GAP__`）只补甘特图时间轴、不计目标。

**第 4 步：补关键动作**（`backend/app/config.py::PART_CONFIGS[part]["key_actions"]`）
——只影响**动作覆盖检查**与异常分析，不影响节点取值。

**第 5 步：补业务时间列**（同文件 `PART_CONFIGS[part]["biz_time_cols"]`）——若第 2 步用了新的系统列。

**第 6 步：前端**——**通常不需要改**。
- 段规则表由 `seg_meta()` 自动生成，配置中心会自动出现新段（可在界面上调目标天）。
- 只有**新增数值型配置键**时才要动：`rule_service.py::_default_rules()` + `RULE_META` + `routers/rules.py::_SIMPLE_KEYS`（**三处缺一，前端保存会 422**）。
- 新节点若要进甘特图分块，看 `seg_rules.py::G_ORDER`。

**第 7 步：同步同源件 B**（`流程复盘/route_check_sys.py`）——在它的 `NODES` / `SEGS` 里加对应定义，并在 `write_notes()` 里补口径说明。

**第 8 步：回归**（见 §7）。

## 3. 新增一个「数据字段」的标准步骤

先分类，三类改法完全不同：

| 字段类型 | 例子 | 要不要改代码 |
| --- | --- | --- |
| **系统业务时间列** | `本地仓到货时间`、`全站点首次上架完成日期` | ✅ 要（挂到 `NODES` + `biz_time_cols`） |
| **审批动作名** | `取得手机数据`、`采购下单` | ✅ 要（挂到 `NODES` 的审批动作位） |
| **纯信息列** | `设计稿图片`、`发货数量`、`是否真机测试` | ❌ **不用改代码** |

**为什么纯信息列不用改**：`backend/app/parser.py::load_part_file()` 用 pandas **读全列**（不硬编码业务列），ETL 把整行原样存进 `part_doc.raw`（JSON）。新增信息列自动落库、自动可查。

**需要注意的三处例外**：

1. **该列是 18 位审批编号 / 长数字 ID** → 必须加进 `backend/app/config.py::TEXT_SAFE_COLS`（否则被 Excel 转科学计数法丢精度）。
2. **该列应视为"通用列"（不属于任何业务环节）** → 加进 `config.py::COMMON_COLS`。
3. **该列若在钉钉导出里是日期字符串** → `TIME_COLS`（`创建时间/更新时间/完成时间`）只在列名固定时才需要加；节点用列由 `NODES` 自己解析，不依赖它。

**验证**：重新导入该批次 → 在「记录」页确认新列有值 → 跑 `pytest tests/ -q`。

## 4. 接入一个新「品类」的标准步骤（含当前缺口）

> 以手机壳为例（数据侧已就绪，后台尚未接入）。

**第 1 步：先探测**（不改任何代码）

```powershell
python scripts/probe_category_columns.py "D:\...\data\手机壳\手机壳" --out scripts\_probe_shell.txt
```

输出四段：① 文件命名合规性 ② 各 Part 列结构 ③ 与手机膜基线的列差异 ④ **节点系统列存在性 + 可替代候选（含填充率）**。
**退出码 1 = 有节点没有系统列**，需按候选列人工确认或改口径。

**第 2 步：确认文件命名合规**（这是个**静默陷阱**）

`backend/app/config.py::list_batches()` 用 `f.name.split("_")[0]` 取 Part 号。所以：

| 文件名 | 结果 |
| --- | --- |
| `Part1_产品开发-20260922.xlsx` | ✅ 识别为 `Part1` |
| `Part1-产品开发-20260922.xlsx` | ❌ `split("_")[0]` = 整名 → **不在 PART_CONFIGS → 静默丢弃** |

手机壳目录**历史上混用过连字符**（`Part2-新品首单下单-*.xlsx`），现已统一为下划线。**新品类导出时必须统一 `PartN_名称-时间戳.xlsx`。**

**第 3 步：数据根要支持多品类**（⚠️ **仍是缺口**）

现在 `DATA_ROOT` 是**单一目录**（生效值在 `D:\apps\data-admin\.env`，指向 `...\data\手机膜`），
`list_batches()` = `DATA_ROOT.iterdir()` → **手机壳批次在后台完全不可见**（实测 `/api/batches` 与 MySQL `batch` 表都只有 4 个手机膜批次）。

需要做的改造（尚未实施）：
- 方案 a：`DATA_ROOT` 支持多根（分号/列表），`list_batches()` 汇总各根
- 方案 b：批次表加 `category` 字段，按品类切换数据根
- 前端目前**零处**提到品类，所以接入不用动前端
- 批次名 → 品类可用 `category_rules.category_of_text(batch_name, batch_path)` 推断（已实现并有测试覆盖）

**第 4 步：按品类分发 `PART_CONFIGS`**（✅ **已完成 2026-09-22**）

`config.py` 现有 `PART_CONFIGS_BY_CATEGORY` + `part_configs_for(品类)`：
- 手机膜 → `config.py::PART_CONFIGS`（保持原样，15 处现存引用零改动）
- 手机壳 → `seg_rules_shell.py::PART_CONFIGS`（列名/关键动作按**真实导出实测**）
- ⚠️ 两个品类的 **9 个 Part 键名与 Part 名完全相同**（导出文件名一致），差异只在
  `key_actions` / `biz_time_cols` / `notes` → **所以 ETL 与 parser 不需要改**。

**第 5 步：按品类分发 `NODES` / `SEGS`**（✅ **已完成 2026-09-22**）

`category_rules.py::rules_for(品类)` → `RuleSet`；引擎默认手机膜。手机壳的实测映射见 §5。

**第 6 步：注意评级与损益的降级**（✅ 已按此实现）

商品资料 A1 明写「**手机壳产品不参与以上产品评级规则**」→ 手机壳 SKU 评级天然为空 → **损益推算走「评级未命中」降级分支**（件数照算、金额 `null`、标 `degraded`）。这是**口径正确**，不是缺数据。

**第 7 步：跑动作覆盖检查 + 品类规则验收**

```powershell
python scripts/check_action_coverage.py "D:\...\data\手机壳\手机壳"
python scripts/probe_category_columns.py "D:\...\data\手机壳\手机壳"
python scripts/verify_shell_rules.py            # 品类规则离线跑通（不依赖入库）
python -m pytest tests/test_category_rules.py -q
```

## 5. 手机壳品类实测映射（2026-09-22 模拟复盘）

### 5.1 缺失节点与可替代性

用手机膜口径的 30 个关键动作去查手机壳，**22/30 命中**，缺 8 个。逐节点实测（`probe_category_columns.py` + 全品类填充率统计）：

| 手机膜节点 | 规范化列 | 手机壳情况 | 候选替代列（实测填充率） | 结论 |
| --- | --- | --- | --- | --- |
| 提案 | `Part1.创建时间` | ✔ 有 | — | 直接用 |
| **取数** | `Part1.手机数据取得日期` | ✘ **列不存在** | `手机数据取得时间`（Part6）**非空 0/7 = 0%** | ❌ **无替代** |
| **签样** | `Part2.全套样品测试完成时间` | ✘ 无此列 | ✅ **`Part1.三方确样时间` 34/34 = 100%**<br>`Part1.全部设计确认时间` 100%<br>`Part1.打样完成时间` 100%<br>`Part2.三方确样时间` 42%（12/28）<br>`Part3.手机壳确样日期` 23%、`Part7.手机壳确样时间` 28% | ✅ **可替代** |
| 采购 | `Part2.首单下单时间` | ✔ 有（60%） | — | 直接用 |
| 本地仓到货 | `Part3.本地仓到货时间` | ✔ 有（53%） | — | 直接用 |
| 首次上架 | `Part4.全站点首次上架完成日期` | ✔ 有（100%） | 亦可用 `是否完成全部站点首次上架` | 直接用 |
| 寄送 | `Part6.寄送拍摄团队日期` | ✔ 有 | — | 直接用 |
| 拍摄交付 | `Part6.拍摄团队素材交付日期` | ✔ 有 | — | 直接用 |
| 素材加工 | （无系统列·用动作） | ✔ 动作名存在 | — | 直接用；**产品部终节点/素材交付** |
| 上架 | `Part7.最终上架完成时间` | ✔ 有（100%） | — | 直接用 |
| 广告 | `Part7.广告上架完成时间` | ✔ 有（100%） | — | 直接用 |

**关键结论**：

1. **「签样」有明确替代**：手机壳的**「确样」是一个跨 Part 同值的节点** —— `Part1.三方确样时间`、`Part2.三方确样时间`、`Part3.手机壳确样日期`、`Part7.手机壳确样时间` 在 K011-008 上**全部等于 2026-01-13**。其中 `Part1.三方确样时间` 填充率最高（100%）→ **首选替代**。
2. **「取数」在手机壳是品类级结构性缺失**：`手机数据取得日期` 列**根本不存在**（0 单据），`手机数据取得时间` 列存在但**全空（0/7）**。不是个别 SKU 缺，是**整个品类没有这个节点** → **最终处理见 §5.2（不列入考核，起点改用提案）**。
3. **「手机上架确认」「新品促销开始」真缺失**：手机壳 `Part8` 无 `手机上架日期`/`到货数量` 列，动作名也只有「到货通知」（58/77）→ **无替代**（业务上手机壳可能不跟随手机上架时间）。

### 5.2 ✅ 考核口径决策（2026-09-22 已定，不再悬置）

手机膜 `ROUTE_TARGETS` 的三条路线**时钟起点都是「取数」**：

```
运营路线 = 取数 → max(上架, 广告)          ≤52 优 / ≤60 底线
空运路线 = 取数 → 最晚空运货件到货          ≤49 优 / ≤60 底线
海运路线 = 取数 → 最晚海运货件到货          ≤69 优
```

### 6.1 ⚠️ 新增品类会踩的三个隐蔽陷阱（2026-09-22 真机踩过，都写进代码了）

**陷阱一：复盘缓存 × KPI 快照的「同线程重入死锁」——会把整个后端永久卡死**

调用链是环形的：

```
get_review_data → record_snapshot → _build_kpi
   → compute_transport / _get_alerts_cached / compute_scenarios
   → get_review_data        ← 绕回起点（同一线程！）
```

原设计靠"嵌套那次必然命中缓存"兜底。**一旦缓存未命中**，嵌套的 `get_review_data`
会在同一线程再次进入 `record_snapshot`，而此时 `history._lock` 已被本线程持有 →
非重入锁自己撞死自己 → `_lock` 永不释放 → 此后所有 `/api/history`、所有复盘重算
全部挂死（HTTP 侧表现为请求永不返回，**不报错、不 500**，最难查的一类故障）。

按品类分规则正好制造了这个未命中：单槽缓存里装着手机壳时，嵌套进来的默认品类
（手机膜）必然未命中。**三个修复点，改品类相关代码时不要退回去**：

| 位置 | 做法 | 作用 |
| --- | --- | --- |
| `review._cache_by_cat` | 缓存**按品类分槽** | 消除跨品类未命中（根因） |
| `history._lock` | `RLock`（不是 `Lock`） | 同线程重入不再自锁 |
| `history._reentry` | 线程局部重入标记，命中直接返回 | 不做无意义的套娃/重复落快照 |
| `alerts._get_alerts_cached` | 计算挪到**锁外**（双检锁） | 同一类风险，它也在锁内回调 `get_review_data` |

**陷阱二：快照跨品类串味 + 去重只看"最后一张"**

- `record_snapshot` 原按 `snaps[-1]` 去重。品类交替访问时"最后一张"总是另一品类 →
  同一个状态被反复追加，历史被刷爆。→ 已改为**按指纹去重**（`for s in reversed(snaps)`）。
- `/api/history` 原用 `review._cache["fp"]`（全进程**最后一格**镜像）取指纹，数据却取默认品类。
  算过手机壳之后再取快照，就会把手机膜的 KPI 挂到手机壳的指纹上。→ 已改为
  `review.fingerprint_for(category)`，**指纹与数据同品类**。
- 当时 `_build_kpi` 的运输/预警/场景看板还没按品类分发 → 一度用
  `history._snapshot_scope_ok()` 把自动快照**限制在默认品类**。现在三个看板
  （`compute_transport` / `_get_alerts_cached` / `compute_scenarios`）都接受 `category`
  且做批次隔离，`_build_kpi` 也透传品类 → **该限制已移除**，各品类各自落快照
  （测例：`test_snapshot_per_category_when_scoped`）。

**陷阱三：`X` 档损益静默算成 ¥0（不是缺数据，是错值）**

`product_rules.GRADE_RANGES["X"] = (0.0, 0.0)`（X = 暂无销售数据）。旧代码只在区间为
`None` 时才走兜底，`(0,0)` 被当成"有效区间"→ 数量/金额全 0。手机壳 24/25 个 SKU 是 X 档，
一接入就踩到。修法见 §5.4；判据：**区间是否为 `(0,0)` 也要走兜底并标注 `degraded`**。
